# DB에서 처리 vs 코드에서 처리 — 판단 가이드

> 새 프로젝트에서 "이 규칙을 DB 제약/트리거로 할까, 코드(도메인)로 할까?"를 올바르게 판단하기 위한 레퍼런스.

---

## 1. DB 측 강제 수단 카탈로그

### A. 선언적 제약 (declarative) — **DB의 본업, 적극 사용**
명시적·원자적·우회 불가·읽기 쉬움. "이 데이터는 항상 유효하다"를 스키마에 박음.

| 수단 | 용도 | 범위 |
|---|---|---|
| **NOT NULL** | 필수 값 | 단일 컬럼 |
| **CHECK** | 한 행 내 조건 (`current ≤ max`, `status IN (...)`, `price > 0`) | **단일 행만** (다른 행 COUNT 불가) |
| **UNIQUE / PK** | 중복 방지 / 식별자 | 단일·복합 컬럼 |
| **FOREIGN KEY** | 참조 무결성 + `ON DELETE` (CASCADE/SET NULL/RESTRICT) | 테이블 간 관계 |
| **EXCLUSION** | 겹침 방지 (예: 시간대 예약 중복 — GiST) | 행 간 (고급) |
| **GENERATED column** (`GENERATED ALWAYS AS ... STORED`) | 같은 행에서 파생값 자동 계산 | 단일 행 |
| **Partial UNIQUE INDEX** (`UNIQUE ... WHERE`) | 조건부 유일성 (예: 유저당 active 1개) | 조건부 |
| **DEFERRABLE 제약 / constraint trigger** | **커밋 시점**에 cross-row 불변식 검사 (set 불변식) | 행 간 (고급) |
| **DOMAIN type** | 재사용 제약 타입 (email 등) | 타입 |

### B. 명령형 (imperative) — **강력하지만 숨김 → 최소화**
| 수단 | 용도 | 주의 |
|---|---|---|
| **TRIGGER** (+함수) | 행 변경 시 자동 부수효과/검증/파생 유지 | **숨은 로직** — 디버그·테스트 어려움. 꼭 필요할 때만 |
| **RPC / stored function** | 명시적 호출(`sb.rpc`), 트랜잭션·원자적 다중작업 캡슐화 | 트리거보다 나음(명시적). 로직이 SQL에 감 |
| **RLS (Row Level Security)** | 행 접근 권한 (SELECT/INSERT/UPDATE/DELETE) | **신뢰 못할 클라가 DB 직접 접근 시 필수** (Supabase) |
| **Transaction isolation** (SERIALIZABLE 등) | 동시성 정합성 | 성능 trade-off |
| **RULE** | 쿼리 재작성 | 사실상 비권장(트리거로) |

## 2. 판단 체크리스트 (순서대로)

각 규칙/불변식마다 위에서부터 물어본다:

1. **구조적 무결성인가?** (참조 / 필수 / 유일) → **DB 선언적** (FK / NOT NULL / UNIQUE / PK). 무조건.
2. **앱이 아닌 경로로 깨질 수 있고 + 치명적인가?** (직접 SQL, 다른 서비스, admin 패널, 데이터 영구 손상) → **DB**.
3. **동시성 race로 깨지나?** (원자성 필요 — 카운터 캡, 중복 예약) → **DB** (제약 / 락 / 원자적 연산). *코드는 요청 간 원자성을 보장 못 함.*
4. **신뢰 못할 클라이언트가 DB에 직접 접근하나?** (Supabase 등) → **DB의 RLS**가 진짜 권한 경계.
5. **위 다 아니면** = 비즈니스 로직 / 워크플로 / 단일 경로 / 표현력 필요 → **코드(도메인)**.
6. **치명적이면** → **코드 + DB 백스톱 둘 다** (defense in depth). 둘 중 택일 아님.
7. **DB에 둬야 한다면** → *선언적으로 가능한가?* 가능하면 CHECK/FK 등. **불가능할 때만** 트리거/함수, 그것도 **명시 RPC 우선**.

---

## 3. 원칙 — "DB 최소, 코드 최대"는 절반만 맞다

당신 방향("꼭 DB여야 하는 것만 DB, 웬만하면 코드")은 **명령형(트리거)에 대해선 맞지만**, **선언적 제약은 줄일 대상이 아니라 DB의 *핵심 책무*** 입니다.

> **DB의 1차 책무 = 데이터 무결성 보장.** 유효하지 않은 데이터를 담을 수 있는 DB는 본업 실패. 그래서 FK/CHECK/UNIQUE/NOT NULL은 "추가 처리"가 아니라 **스키마의 일부**다 (관계형 기본 원칙).

정확한 재정식화:
- **선언적 제약 → DB.** 항상. (CHECK는 코드 룰과 *경쟁*이 아니라 *최후 방어선*)
- **비즈니스 로직 / 워크플로 / 권한 결정 → 코드(도메인).**
- **명령형 DB(트리거) → 최소화.** 동시성·cross-row 유지·전(全)경로 보장이 *필요할 때만*, 그리고 가능하면 **명시 RPC**로.
- **치명적 불변식 → 코드(UX·로직) + DB 제약(백스톱).**

논쟁의 대상은 오직 **"명령형 로직(트리거/함수가 비즈니스 워크플로를 수행)"** 입니다. 그건 코드로. 선언적 무결성은 논쟁 대상이 아님.

## 4. 실무에서는

- **CHECK / FK / UNIQUE / NOT NULL**: 거의 모든 팀이 DB에. 호불호 없음.
- **트리거**: **호불호 갈림.** 다수 시니어가 싫어함(숨김·테스트난이·spooky action) → 명시 코드/RPC 선호. "트리거 최소화"는 널리 공유되는 본능.
- **카운트/비정규화 유지**: 갈림 — 트리거 / 앱 트랜잭션 / generated column.
- **동시성 불변식(카운터 캡 등)**: 원자적 조건부 UPDATE(`+1 WHERE current<max`) 또는 `SELECT FOR UPDATE` 트랜잭션 — DB 차원. 코드만으론 race.
- **RLS**: 클라가 DB 직접 접근하는 스택(Supabase)에선 **필수**. 앱 권한 체크가 있어도 RLS가 최후 경계.
- **권한·워크플로**: 코드(도메인).

## 5. 새 프로젝트 셋업 순서 (이대로 하면 됨)

1. **스키마 = 무결성 먼저**: 테이블 모델링하며 NOT NULL / PK / FK(+ON DELETE) / UNIQUE / CHECK / (필요시 EXCLUSION) 다 선언.
2. **RLS 전 테이블에** (클라 직접 접근 시): deny by default + 명시 정책.
3. **도메인 레이어 = 비즈니스 로직**: rich domain model, use-case. 룰은 코드.
4. **트리거/함수는 예외적으로만**:
   - (a) 동시성-원자 연산 → **명시 RPC**
   - (b) 선언적으로 표현 못 하는 cross-row 무결성 → constraint trigger / deferrable
   - (c) generated column으로 안 되는 파생/비정규화 유지
5. **defense in depth**: 치명 불변식은 코드 + DB 제약 둘 다.
6. **DB 전부 버전관리** (migrations): 제약·RLS·함수 포함. (트리거가 repo에 안 보이면 위험 — `docs/supabase-cli-guide.md` 참고)
7. 규칙마다 **2번 체크리스트** 적용.

## 6. 트리거: 남길 것 vs 명시화할 것

"트리거 최소화"는 **"트리거 0"이 아니다.** 문제는 **숨겨진 *비즈니스 결정***일 때고, **횡단 관심사**(updated_at, audit)는 오히려 트리거가 정석.

| 트리거 종류 | 예 | 판정 | 이유 |
|---|---|---|---|
| **기계적 횡단** | `updated_at = now()` | ✅ **유지** | 비즈니스 결정 아님. 코드로 옮기면 모든 update가 직접 set → 빠뜨림. 한 곳에 모으는 게 안전 |
| **감사 로그(audit)** | 변경 이력 기록 | ✅ **유지(정당)** | 모든 경로에서 보장(우회 불가). 코드 곳곳에 흩으면 누락 |
| **비즈니스 워크플로 부수효과** | "수락되면 채팅 합류" | 🔁 **명시화**(RPC/앱) | 숨은 *도메인 결정* → 도메인에서 보여야 |
| **동시성 카운트/캡 유지** | `current ±1`, 캡 | 🔁 **원자적 RPC**(조건부 update / FOR UPDATE) | race-safe + 명시적 |
| **파생 데이터** | `status = full ? completed : recruiting` | ❌ **제거** → generated column / read 계산 | 저장-유지보다 *계산*이 안전(드리프트·split-brain 없음) |
| **중복 reject** | 트리거가 CHECK와 같은 거부 | ❌ **제거** | CHECK가 이미 함 |

**판별 한 질문**:
> **"이 트리거가 *비즈니스 결정*을 숨기나, 아니면 *횡단 관심사*인가?"**
> - 비즈니스 결정(워크플로·도메인 룰) 숨김 → **명시화**(RPC/앱).
> - 횡단 관심사(updated_at·audit) → **트리거가 오히려 한 곳에 모아 안전.**

## 7. 한 줄 요약

> **무결성(참조·유일·필수·범위)은 DB의 본업 → 선언적 제약으로.**
> **로직·워크플로·권한은 코드(도메인)로.**
> **명령형 DB(트리거)는 동시성·cross-row·전경로보장이 *강제할 때만*, 그것도 명시 RPC로.**
> **치명적인 건 코드 + DB 백스톱 둘 다.** "DB 최소"는 *트리거*에만 적용, *제약*엔 적용 안 됨.
